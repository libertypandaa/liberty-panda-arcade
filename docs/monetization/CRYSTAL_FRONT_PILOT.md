## Минимальный продукт пилота

Предлагается одна существующая Bomb: `gameId=crystal-front-demo`, `productId=cf.bomb.single`, `itemId=bomb`, `kind=consumable`, quantity 1. Имя SKU — предложение; цена LPA должна быть утверждена отдельно в серверном каталоге. Число 35 из local Rays автоматически в LPA не переносить. Для контролируемой приёмки использовать отдельные тестовые аккаунты/каталог и помеченные тестовые средства, не публичную бесплатную выдачу.

Поток: открыть магазин → запросить capabilities, wallet, catalog, inventory → показать единственный допущенный сервером товар → сохранить operationId → SDK purchase → подтверждение цены оболочкой → серверное списание и grant → сверить inventory → сохранить применение grantId ровно один раз → отобразить доступную бомбу. При недоступной сети/аккаунте/провайдерах показывать реальное состояние. Ни локальный success, ни анимация покупки не дают предмет.

Для режима LPA отключить локальный `buyBonus` для этого товара, mock reward и фальшивые денежные пакеты. Остальные локальные бонусы можно сохранить как наследуемый некоммерческий прогресс, ясно отделённый от подтверждённых grant. Старые Rays нельзя импортировать в общий кошелёк и выдавать за заработанную серверную валюту; локальный рейтинг также не импортируется в глобальную таблицу. Для standalone сохранить существующий игровой режим без обещания аккаунтных покупок.

## Что требуется от игры и хаба

1. **Игровой адаптер**: новый модуль рядом с main.js импортирует зафиксированную копию `game-platform-sdk.js`; использует только разрешённые SDK методы. Main подключает адаптер в renderShop/buyBonus и Exit. Core сохраняет правила взрыва, но получает подтверждённый доступный запас через явную команду/адаптер, а не прямой импорт SDK в core.
2. **Контекст владельца**: игра сейчас не знает аккаунта, SDK не отдаёт токен/userId. Для безопасных локальных ключей нужен хостовый непривилегированный стабильный `storageNamespace` на пару account/game и lifecycle смены аккаунта. Он не принимается сервером как авторизация. Хаб выбирает namespace, закрывает iframe при смене пользователя; offline cache открывается только в ранее связанном контексте. Не читать parent Supabase или токены.
3. **Миграция локального формата**: отдельный versioned account/game save envelope, pending purchases, applied grant IDs и usage journal. Старый `crystalFrontProgressV1` сохранить как legacy backup. Не присваивать его автоматически любому вошедшему пользователю. Решение о переносе игрового неэкономического прогресса принимать отдельно; не превращать legacy bonuses в серверные покупки.
4. **Сейв до выхода/обновления**: ошибка сохранения должна отменять закрытие, а не быть проглоченной; отложить обновление при активном матче, незавершённой покупке или синхронизации. Не менять текущий SDK сайта ради одного игрового исключения.

## Недостающий серверный контракт consumable + save

Существующих `purchase/inventory` недостаточно: повторное чтение всех когда-либо выданных grant не должно восстанавливать уже потраченные бомбы. Нужны утверждённые операции поверх серверных grant, а не загрузка абсолютного `bonuses.bomb` из localStorage.

- **Снимок прогресса**: сервер возвращает собственные game save, schemaVersion, saveRevision, inventory/grant cursor и непривилегированный storageNamespace; actor берётся из авторизации. Не отдавать записи другого пользователя.
- **Атомарная отправка ветки**: `{submissionId, baseRevision, schemaVersion, save, results[], consumptions[]}`. Для расхода: grantId, itemId, количество, уникальный usageId/matchId. Сервер сверяет принадлежность, доступный остаток, предельные значения и запрещает отрицательные расходы/создание grant клиентом. Одна транзакция либо принимает новую ревизию и весь связанный расход/рейтинг/результаты, либо отклоняет всю устаревшую ветку. Клиентская версия «2» сама по себе ничего не доказывает.
- **Идемпотентность**: повтор submissionId с тем же телом возвращает прежний ответ; изменённое тело — конфликт. Принятый matchId не повышает рейтинг дважды даже при другом submissionId. Аналитический match_end не является разрешением начислить награду.
- **Конфликт двух offline устройств**: A и B стартуют от revision 1 и могут локально использовать одну и ту же бомбу. Первый корректный upload становится revision 2. Второй получает conflict + канонический save/inventory; его расходы, результаты, рейтинг и игровые награды не применяются. Его локальная ветка заменяется серверной, а не складывается с ней.
- **Покупки независимо от веток**: grant/receipt из онлайн-покупки хранится вне откатываемого save. При конфликте сохранить новые, ещё не отражённые в принятой ветке grant по cursor/ID; нельзя потерять оплаченную бомбу, купленную после исходного snapshot. При принятии старой ветки reconcile с текущим ledger, не заменять баланс/инвентарь её абсолютными значениями.

До этого контракта допустим закрытый технический тест покупки/receipt/inventory, но нельзя объявить готовой публичную продажу расходуемой бомбы с корректным offline расходованием. Более узкий online-only consume требует отдельного решения и не заменяет согласованную офлайн-модель.

## Rewarded ad intent

Первый UI-пилот: добровольная кнопка «Посмотреть ролик за награду» только при разрешённой server capability. При `providers=false` не запускать mock и не начислять LPA. Награда и placement — серверные настройки; текущие 40 local Rays не являются коммерческим обещанием.

Требуемый будущий контракт: create intent с game/placement/requestId, серверная привязка actor и фиксированной награды/срока действия; показ через одобренный provider adapter; проверенный сервером callback/transaction даёт одну ledger credit; poll/recover intent возвращает pending/rewarded/cancelled/no_fill/failed. Клиентский `adCompleted`, таймер или закрытие overlay не являются доказательством просмотра. Повтор callback, смена аккаунта и lost response не дают повторной награды. SDK сайта сейчас не содержит публичного rewarded-ad метода — не придумывать вызов в игровом коде до согласования.

## Публикация и ближайшая задача

`docs/DEMO_RELEASE.md`: исходный репозиторий только проверяет source (test/build); push туда не обновляет публичную игру. `prepare-demo-release.mjs <sourceSHA>` создаёт разрешённый bundle; перенос через GitHub connector в `crystal-front-demo/main`, проверка source tree/manifest, без force и с сохранением публичного Pages workflow. Последний workflow публичного repo запускает core/cascade tests, verifier и публикует собранный public artifact. Веб-источник: https://libertypandaa.github.io/crystal-front-demo/. Версию LPA и версию игры учитывать отдельно.

**Ближайшее исполнимое поручение агенту игры после разрешения менять исходники:** вынести commerce adapter и account-scoped save envelope с явной обработкой storage errors; подключить текущие SDK wallet/catalog/purchase/inventory и безопасный Exit; в отдельном управляемом тесте проверить одну Bomb с fake transport, реальными operation/grant IDs и повторным receipt без удвоения. Не включать реальную рекламу, не конвертировать legacy Rays и не публиковать платный offline consumable до готовности серверного consume/revision. Параллельно агент БД специфицирует/тестирует атомарный save/usage commit. Затем интеграционный тест двух устройств/аккаунтов, реальной покупки тестового SKU, потери ответа, расхода и восстановления, и лишь после приёмки controlled public build.
